# Migration to runtime 1.1.0

Runtime **1.1.0** adds behavior-preserving AI refactoring as a backwards-compatible capability.

## Compatibility

No migration is required for normal feature workflows.

- `workflowFormatVersion` remains **1**.
- `artifactSchemaVersion` remains **1**.
- Existing feature runs continue to use normal feature mode.
- The new refactor-only stages are conditional and are skipped for ordinary feature requests.

## New refactor mode

The engine detects common refactoring intent automatically, or you can force the mode:

```bash
npm run workflow:start -- RF-001 \
  --request "Refactor login validation without changing behavior" \
  --mode refactor \
  --scope mobile
```

For refactor runs, the workflow now adds:

```text
behavior baseline
→ preservation invariants
→ characterization coverage gate
→ specialist analysis
→ incremental refactor plan
→ human approval
→ checkpointed implementation
→ build/test using a scope-aware verification matrix
→ independent behavior regression review
→ fixes
→ behavior-equivalence verification
→ final verification
```

## New commands

```bash
npm run workflow:refactor:coverage -- waive <run-id> <behavior-id> --reason "..." --owner "..."
npm run workflow:refactor:checkpoint -- <run-id> <increment-id> --diff "..." --test "..."
npm run workflow:refactor:report -- <run-id>
npm run workflow:refactor:report -- <run-id> --json
npm run workflow:refactor:gates:selftest
npm run workflow:refactor:equivalence:selftest
```

## Behavioral-equivalence semantics

A refactor is rejected when the runtime detects an unexpected behavior change or an undeclared stable-contract change.

A run may report **partial** verification when some scenarios are explicitly unverified. In that case the runtime does not claim full behavioral equivalence, and the GitHub verification summary reports the partial state.
