# 1.9.31 — The kit opens the pull request after verification

Runtime 1.9.31 adds a final `pull-request` stage to `ai/workflows/feature.yaml`, after `verification`. It also adds the read-only `pr-description` role and its contract, the `pull-request` artifact schema, `ai/workflow/pull-request.js`, the `agentic pr` command and `runs.js pull-request-options`. `worktree.json` now records `baseBranch`. The progress views, `github-verification.js` and the agent capability guard change too. The release also adds notifications and a "needs you" banner, the dashboard's `R`/`T` keys, one engine per run, repeated-failure detection, and `retry` for conditional roles: new `ai/workflow/notify.js`, `ai/workflow/repeated-failure.js` and `ai/workflow/engine-owner.js`. The stages before `verification`, the human gates, executor routing and the retry policy are unchanged.

## What changes for you

- **Nothing is pushed unless you turn it on.** A project without a `pull_request` block in `.agentic/config.yaml`, or with `enabled` not exactly `true`, gets the new stage skipped after verification. The progress view then says `Pull request: not opened — run: agentic pr <run-id>`. `agentic init` never rewrites an existing config file, so existing projects do not get the block; add it by hand (see below).
- **With `enabled: true`**, once verification passes the runtime:
  1. asks `pr-description` for the title and body, which fill the repository's PR template if it has one;
  2. commits the run worktree (`git add -A`, respecting `.gitignore`) with the repository's own git identity, with your hooks running;
  3. scans every commit the push would publish (yours, a hook's, or a pre-created branch's, and their messages), then pushes `HEAD` to `ai/<run-id>` (configurable), never forced — or, when no branch is configured, to the branch the worktree already tracks, so an open PR from it is reused;
  4. opens the PR against the branch the run started from.

  A secret in the staged diff or in a commit to be pushed, a conflict marker, a diverged remote branch, an open PR against a different requested base, a missing tool or missing credentials blocks the stage with the reason, and `agentic resume <id>` continues from where it stopped.
- **`agentic pr <run-id>`** opens the PR on request, even while the block is disabled. An unknown or mistyped option (for example `--dryrun`) is refused before anything runs. Use `--base <branch>` for a stacked PR (the base is another PR's branch, which must already be pushed), `--branch <name>` for another branch name, `--draft` for a draft, and `--dry-run` to see what would happen without committing, pushing or calling a provider. The options are kept in the run state, so a later `resume` uses them.
- **Runs that already verified** have no `pull-request` phase in their `state.json`. They get it as pending. `agentic resume <id>` opens their PR only when `pull_request.enabled` is `true`; otherwise the stage is skipped, and `agentic pr <id>` opens it on request. Enabling the block after the stage was skipped is not enough: `resume` does not revisit a skipped stage, so run `agentic pr <id>`.
- **Closed runs that predate the stage** still show 100% and get no `agentic pr` hint, because their PR may have been opened by hand. `agentic resume` of a closed run never opens a PR, and `agentic pr <id>` refuses a closed run unless you pass `--reopen` (check for an existing PR first). Abandoned runs leave the stage out of their percent.
- **The run directory gets `12-pull-request.json` and `12-pull-request.md`**, and `state.json` gets `pullRequest` and, after `agentic pr`, `pullRequestOptions`.
- **The PR line appears in the progress terminal** (`agentic status <id>`, `agentic progress`, the dashboard) as `Pull request: #<number> <url>`, right under the progress bar.
- **You get a desktop notification when a run needs you.** The engine sends it when a stage blocks or fails, when the plan waits for approval, when architecture selection or specialist conflicts wait for you, when the run completes and when `agentic pr` opens a PR. It names the stage, gives a one-line reason and the exact next command. It uses `osascript` on macOS and `notify-send` on Linux when installed; elsewhere nothing is sent, and nothing uses the network. Each event is shown once, and a resume that stops on the same block stays quiet. Secrets are redacted before the text is shortened, and the command is never cut. It is on by default; turn it off in `.agentic/config.yaml` (below). Eval runs never notify.
- **`agentic progress` shows what each run needs.** A `⚠` in the run list marks every run waiting on you, and `●` marks a run whose engine is running. The selected run gets a banner with the reason and the whole command. The terminal rings its bell for each new event (and only rings; the desktop notification comes from the engine). `R` resumes the selected run in the background and `T` retries it, then resumes. Plain `r` still refreshes. Their output goes to `<run>/engine/background.log`. Both refuse while an engine for that run is alive. `R` on a run whose stage needs a retry first, or that waits at a gate, starts nothing and says what to press or run. Plan approval has no key: run the command the banner shows. `agentic status <id>`, `runs.js status`, `agentic runs` and the Markdown view show the same line. The published GitHub progress comment shows the headline and command but not the reason.
- **Two engines can no longer drive one run.** While an engine works on a run, `<run>/engine/engine.pid` names it. A second `agentic resume`/`retry`/`pr` for that run refuses and says which pid holds it. A record whose pid is now an unrelated process (reused after a crash, or not a node process at all) does not count. If the refusal is wrong anyway, it names the file to delete.
- **A failure that repeats says so.** When a stage, role or conditional role fails with the same reason as last time (timestamps, paths and attempt ids ignored), its state entry gets `repeatedFailure: <n>`. The banner, `status` and the notification then say "Same failure as last time — this needs a fix outside <stage>". Retrying it again is still allowed.
- **`resume` leaves a spent stage alone.** A failed stage, or a failed role of a parallel stage, that its retry policy will not re-attempt (a deterministic failure, attempts used up) is not begun again by `resume`. It keeps its real reason and the engine prints the `retry` command. Before, it failed again with `max attempts exhausted`. `agentic retry` resets it as before.
- **`agentic retry <id>` also resets conditional roles.** A blocked `verification/mobile-evidence` is reset with the rest, or alone with `agentic retry <id> mobile-evidence`. Before, retry said "nothing to retry". When there really is nothing to retry, the message names what would move the run, for example `nothing to retry; run agentic resume <id>`. mobile-evidence now records its own error as the block reason instead of `node … failed with exit 1`.
- **`state.json` gains** `notifications.sent` (event keys already shown, the last 200), and `lastFailure`/`repeatedFailure` on phase, role and conditional entries. Older runs work as they are.
- **Agent roles can no longer push or open PRs.** Inside an engine-launched agent, `git push` (with or without global options such as `-C` or `-c`), `gh pr create`, `agentic pr` and calls to the pull request APIs are denied for every role, and the agent's git environment sends any push to an unreachable URL. Before, `implementation` and `fixes` could run `git push`. Your own interactive sessions follow `ai/guard.yaml` as before.

## Action required

None, to keep today's behaviour.

To have PRs opened automatically, add this to the project's `.agentic/config.yaml` (in the main checkout, not a run worktree):

```yaml
pull_request:
  enabled: true         # true = open the PR automatically after verification
  provider: auto        # auto | github | bitbucket  (auto = from the remote URL)
  remote: origin
  base: auto            # auto = the branch the run's worktree was created from
  branch: "ai/{id}"     # template for the pushed branch; {id} = run id
  draft: false
```

Then make the provider usable in the shell that runs `agentic`:

- GitHub: install `gh` and run `gh auth login`, or export `GH_TOKEN`.
- Bitbucket Cloud: export `BITBUCKET_EMAIL` and `BITBUCKET_API_TOKEN` (an Atlassian API token with pull request write scope), or `BITBUCKET_USERNAME` and `BITBUCKET_APP_PASSWORD`.

The run worktree's repository needs a git identity (`git config user.name` / `user.email`); the runtime never sets one.

Notifications need no action. To turn them off, add this to the same `.agentic/config.yaml` (main checkout):

```yaml
notifications:
  desktop: false        # no desktop notifications from the engine
  bell: false           # agentic progress does not ring the terminal bell
```

On macOS, if no notification appears, check System Settings → Notifications for Script Editor, the app macOS usually attributes `osascript` notifications to. On Linux, install `libnotify` (`notify-send`) to get them.

Runs created before 1.9.31 have no `baseBranch` in their worktree metadata, and neither does a run whose `ai/run/<id>` branch you created beforehand from another base. Their base comes from `<remote>/HEAD` only when the run demonstrably starts on it (the run's start commit is on that branch and the run branch was created at that commit, per its reflog). Otherwise the stage blocks and asks you to pass `--base <branch>`: a wrong guess would open a PR carrying another branch's commits.
