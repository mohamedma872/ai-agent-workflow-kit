# 1.9.30 — Parallel stages run their roles at the same time

Runtime 1.9.30 changes `ai/workflow/engine.js`, the state writers (`ai/tasks/feature/runs.js`, `ai/workflow/attempts.js`, `ai/tasks/feature/mobile-evidence.js`) and the progress view, and adds `ai/workflow/state-lock.js` and `ai/workflow/parallel-roles.js`. The workflow stage graph, role selection, prompts, executor routing, retry/fallback policy, gates, guard rules and artifact schemas are unchanged.

## What changes for you

- **`analysis` and `reviews` are faster.** Their selected roles now run at the same time, at most 4 at once, instead of one after another. A run with 9 analysis roles that took about 25 minutes should take about as long as its slowest role.
- **More agents run at once.** With the default cap, up to 4 `claude -p` (or codex) sessions run together during these stages. That uses more of your rate limit and machine at the same moment. Total cost is the same.
- **Interleaved output.** Each line of a role's output starts with `[role]`. Each role's output still appears when that role's agent finishes.
- **A failure no longer stops the other roles.** The stage waits for all of them, then fails once and names every failed role. Before, it stopped at the first failure and left later roles unstarted. With a cap of 1 it still stops at the first failure.
- **`behavior-regression-review` still runs last.** It reads the other reviews' findings, so it starts only after the concurrent reviews have all passed. So does any role whose contract lists `validated_review_findings` as an input.
- **A running stage stays `in_progress`.** The progress view, dashboard and `runs.js status` show the stage as `in_progress` while any of its roles runs, even after a sibling has failed. The failure shows when the last role finishes.
- **Stopping a run stops its agents.** Ctrl-C, a signal to the role runner, or the engine process dying stops every running role and the agent under it. An agent that ignores the signal is killed after 10 s. If the role runner itself is killed outright, the engine and each role process stop the roles instead. The stopped roles are marked failed with `interrupted: <signal|parent-exit|SIGKILL>`. `resume` starts them again.
- **`retry` waits for a running stage.** While the roles of a stage run, `engine/<stage>-parallel.pid` in the run directory holds the role runner's pid. `runs.js retry` (and `agentic retry`) refuse to reset a role of that stage that is still `in_progress` while that process is alive. Wait for the stage to finish, or stop the run, then retry.
- **State writes take a lock.** A `state.json.lock` directory appears next to `state.json` for the few milliseconds a transition takes. A lock left by a crashed process is taken over when its pid is dead. A lock whose holder is still running is never taken over, however old; only a lock written from another host is taken over after 60 s.

## Action required

None. To keep the old one-at-a-time behaviour, set `AI_WORKFLOW_MAX_PARALLEL=1`. To allow more roles at once, set a higher value, or add `max_parallel: N` to the stage in the workflow file.

If a workflow command ever reports `timed out … waiting for state lock … held by pid N`, check that pid. If no workflow process is running, remove the named `.lock` directory.

If `retry` reports that a role `is still running in the workflow engine (parallel role runner pid N)`, the stage really is running. Wait for it, or stop that process. A pid file left behind by a crash does not block `retry`.

## Check

```bash
node ai/workflow/state-lock.js --selftest
node ai/workflow/parallel-roles.js --selftest
node ai/workflow/engine.js selftest
node ai/tasks/feature/runs.js selftest
```
