# 1.9.35 — Conflicts wait for you, decisions bind the plan, tests run again after fixes

Runtime 1.9.35 changes `ai/workflow/engine.js`, `ai/workflow/progress.js`, `ai/workflow/conflicts.js`, `ai/workflow/conflict-tracker.js`, `ai/workflow/dashboard.js`, `ai/workflow/runs-index.js`, `ai/workflow/notify.js`, `ai/workflow/pull-request.js`, `ai/workflow/subagent-context.js`, `ai/workflow/artifacts.js`, `ai/cli/agentic.js`, `ai/tasks/feature/runs.js`, `ai/tasks/feature/mobile-evidence.js` and `ai/tasks/feature/evidence-attestation.js`, and adds `ai/workflow/engine-launch.js`. The workflow gets one new stage (`post-fix-build-test`), the role contracts one new input (`conflict_decisions`), and the plan schema one optional field (`conflictDecisions`).

## What changes for you

- **Open conflicts are a wait, not a failure.** When `05-analysis/conflicts.json` has unresolved entries, the plan stage stays pending and the engine returns `waiting`, as it does at plan approval. It prints `⚠ Needs you: N conflicts need your decision`, the ids with their topics, and the commands: `agentic resolve <id> <conflict-id> --decision "..." --rationale "..."`, then `agentic resume <id>`. The desktop notification says the same. `agentic resume` and `agentic feature` exit 0 there; before 1.9.35 they exited 1 with `plan blocked by unresolved subagent conflict(s)`. A script that relied on that exit code should check `agentic status <id>` instead.
- **CURRENT says what waits.** The run list, the dashboard and `agentic progress` show `Waiting for conflict decisions` instead of `Waiting for Implementation Plan`. Pressing `R` in `agentic progress` names the decision and the command. `agentic conflicts <id>` ends with the exact resolve and resume commands.
- **One more notification after upgrading.** The notification key now names each conflict's finding pair, so a run blocked on conflicts under 1.9.31 is told once more after the upgrade. A re-arbitration that blocks on a different pair is told again; a refresh never is.
- **Decisions bind the plan.** The plan, implementation, reviews that read the plan, fixes and behavior-equivalence get a "Binding conflict decisions" section with every resolved conflict: its findings, the decision, the rationale and who decided. An engine-run plan must cite each resolved conflict id in `06-plan.md`, normally in the new "Conflict decisions applied" list. A plan that leaves one out fails with `$.conflictDecisions: missing CONFLICT-00N`, is not written, and is kept at `engine/plan-orchestration.rejected`. Run `agentic retry <id>`: the next attempt is told which ids it missed. Plans you edit by hand, and `agentic approve`, are not re-checked.
- **Decisions are made before the plan.** `agentic resolve` refuses once the plan has passed, because the approved plan would still say otherwise. Rework the plan first (`agentic retry <id> plan`), then resolve and resume. A decision carried over a re-arbitration takes the conflict's new id, so ids in `conflicts.json` stay unique; an id that still names two entries (a file from 1.9.31) is refused until the next resume renumbers it.
- **Build + Tests again after fixes.** The new stage `post-fix-build-test` (label "Post-fix Build + Tests") runs qa-execute again after `fixes` when the worktree differs from the tree the last build/test pass saw, recorded in `state.testedWorkspace`. When fixes changed nothing it is skipped with `fixes changed no files since build-test passed`. Its result is `10-post-fix-build-test.md`/`.json`. A failure is retried with `agentic retry <id>`, which resets only that stage; `agentic retry <id> fixes` reworks fixes and resets it too. Runs in flight when you upgrade have no recorded tree, so they run it once before verification. Runs whose verification already passed count it as skipped, until `agentic retry <id> fixes` reworks them. Runs driven by the `/feature` skill or by hand never record the stage, and mobile evidence runs for them as before.
- **Untracked build output counts as a change.** The fingerprint includes untracked files that are not gitignored. If a build directory in your repository is untracked and not ignored, add it to `.gitignore`, or a fixes stage that runs a build triggers the re-run.
- **`agentic approve <id>` returns at once.** It prints the plan digest (counts, the head of the summary, the file), records the approval and starts the engine in the background: `▸ resuming <id>… engine pid N · log .agentic-runs/<id>/engine/background.log`, then `follow: tail -f …`. The `→ next: agentic resume <id>` line that `runs.js approve` ends with is printed only with `--no-resume`, when nothing follows. Before 1.9.35 it blocked the terminal until the engine stopped. A script that relied on that adds `--wait`; `--no-resume` records the approval only. Any other flag after the id is refused.
- **The gate shows the plan.** `agentic status <id>`, `runs.js status`, the dashboard banner and the engine's own stop message print the digest at the approval gate: `Plan: 9 steps · 23 acceptance criteria · 11 risks · REVIEW AMENDMENTS present`, up to six `│` lines of the summary (secrets redacted, at most 600 characters; the dashboard wraps them to its pane, so a one-paragraph summary fills the rows instead of one cut row) and `Full plan: <path>`. The desktop notification and the published GitHub comment do not. In `agentic progress`, `P` opens the plan in `$PAGER` and `A` approves after you answer `y`, then resumes in the background; no key approves on its own.
- **Every needs-you ends with `Commands:`.** Under the headline, reason and command, every surface lists the commands that move the run on (`retry`, `retry <role>`, `resume`, `pr`, `approve`, `rework plan`, `select`, `conflicts`, `resolve`), then `status`, `doctor`, and the engine log, the stopped stage's artifact and the rejected agent output when they exist. The engine prints the block once per stop (so a background engine's `engine/background.log` carries it); the conflicts stop that used to print the needs-you lines inline prints its sentence first and the block right after. The desktop notification's body carries the short form between the reason and the command, whole items only.
- **A stage whose engine died is named.** A stage left `in_progress` with an `engine/engine.pid` record that no live process holds shows `<Stage> is in progress but its engine (pid N) is gone` with `agentic retry <id>` (resume for the pull request) and the block. `retry` resets it. Runs driven by hand or by the `/feature` skill never write the record, so they are never called stalled.
- **Open, verified runs with `pull_request` disabled read as complete.** With verification passed, the stage pending or absent, no `pull_request.enabled: true` in `.agentic/config.yaml` and no `agentic pr` request, the stage shows `skipped — pull_request disabled (open one with: agentic pr <id>)` and the run is 100% `Done`. Runs verified under 1.9.30 or earlier that are still open no longer read 93% "Waiting for Pull Request". `agentic resume <id>` records the skip once and completes; `agentic retry` says the run is complete; the dashboard's `R` refuses on a complete run and names `c` and `agentic pr <id>` (the launcher's own command line names the close command instead). Enabling the block later flips such runs back to waiting, by design: the stage then has work, and `agentic resume` opens the PR. Closing such a run keeps it at 100% `Done`: its stored `pending` pull-request status reads as skipped once the run is closed, like a run closed before the stage existed. A block that does not parse (`enabled: "yes"`, broken YAML) does not count as disabled: the run keeps waiting for the pull request and `agentic status <id>` lists the problem under `State reconciliation` (`.agentic/config.yaml: …`), the same text the engine records when it skips.
- **Stalls are only claimed for engines this host can check.** A run whose `engine/engine.pid` names another host is never called stalled from here, however old the record; before, it read as gone after six hours with a retry offered that would have reset the stage under the engine still working on that host. Role names from `state.json` are filtered like stage ids before they become `retry <role>` commands, file probes or printed text.

- **Built on 1.9.34.** Everything 1.9.32–1.9.34 added (agent activity, `agentic why`, the pinned Flutter SDK, the analyzer baseline, the deletion guard, notification click, base repair) is in this release too. The `Commands:` block also lists `why` when the agent's rejected report exists and `notes` when `notes/<stage>.md` does; the post-fix re-run gets the analyzer comparison; the `Verified — no pull request recorded yet` banner appears only while `pull_request` is enabled.

## Action required

None. Restart any `agentic progress` window and any engine started before the upgrade: a process left running keeps the old code. If a script runs `agentic approve <id>` and expects it to block until the engine stops, add `--wait`.
